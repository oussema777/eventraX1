Critical Finding
The platform ships a single 3.6MB JavaScript bundle with zero route-level code splitting. All 42 pages, 18,683 lines of translations (3 languages), and 10 design studio modals are loaded on every page visit — including the public landing page. On 3G networks, this translates to ~8 second load time with a projected 20% bounce rate increase.
Database Warning
350+ Supabase queries across 41 tables with zero client-side caching. No React Query or SWR integration. Every page navigation re-fetches all data. The event stats hook alone fires 13 queries per call. Multiple N+1 patterns (sponsor reordering, session conflict checks) will cause exponential slowdown at scale.

Critical Issues
N+1 Patterns & Query Anti-Patterns
  1. 01
    Unfiltered Full Table Scan
    CRITICAL
    BusinessProfilePage.tsx:304 executes supabase.from('business_profiles').select('*') with no WHERE clause. Returns ALL business profiles in the database. At 10,000 businesses, this fetches ~50MB of data per page load.
    Fix: Add .eq('owner_profile_id', user.id) or implement pagination with .range(0, 20)
  2. 02
    Sponsor Reorder N+1
    CRITICAL
    useSponsors.ts:221-235 — Makes individual UPDATE queries for each sponsor during drag-and-drop reordering. 20 sponsors = 20 sequential database calls with ~50ms each = 1 second blocking operation.
    Fix: Use Supabase RPC with batch UPDATE or Promise.all() with concurrent updates
  3. 03
    Session Conflict Check Per-Operation
    HIGH
    useSessions.ts:97-102, 156-161 — Every session create/update triggers a full SELECT to check venue conflicts. With 50 sessions in an event and 5 venues, this scans 250 rows per operation.
    Fix: Cache sessions locally, check conflicts client-side, or use DB constraint
  4. 04
    Event Stats — 13 Queries Per Load
    HIGH
    useEventStats.ts:67-285 fires 10 parallel queries + 2-3 conditional sequential queries. Zero caching means navigating between tabs re-fires all 13 queries. With 1000 concurrent dashboard users: 13,000 queries.
    Fix: Implement React Query with staleTime: 300000 (5 min cache), or create a DB view
  5. 05
    My Events Dashboard — No Pagination
    HIGH
    02_My_Events_Dashboard.tsx:30-39 — Fetches ALL user events with .select('*') and no .limit(). Power users with 100+ events will download megabytes of event data including full JSON settings on every navigation.
    Fix: Add .range(0, 20) pagination and select specific columns only
  6. 06
    Browse Events Waterfall
    MEDIUM
    BrowseEventsDiscovery.tsx:101-150 — 4 sequential API calls: getUser → getProfile → getEvents → getTickets. Each waits for the previous to complete. Total waterfall: ~250ms. Could be parallelized to ~80ms.
    Fix: Use Promise.all() for independent queries, prefetch auth from context
