# Private/Public Event Visibility Feature — Design Spec

**Date:** 2026-04-04
**Status:** Draft
**Approach:** Approach A — Boolean `is_public` + `access_code` column

---

## Overview

Add the ability for event organizers to mark events as **Public** or **Private** during event creation. Private events remain visible in browse/discovery but require an **access code** to register. The access code is auto-generated by the system and customizable by the organizer.

## Requirements

1. Organizer selects Public or Private in Wizard Step 1 (core event property)
2. Private events get an auto-generated access code, editable by organizer
3. Visibility choice is reviewed/editable in Wizard Step 4 (PrivacySection)
4. Private events show a "Private" badge on browse event cards
5. Private events show a "Private" badge on the event landing page
6. Registration for private events requires entering the correct access code
7. Public events behave exactly as they do today (no access code needed)
8. All UI text supports EN/FR/AR translations

## Database Schema

### Existing column (no change needed)
- `events.is_public` — `BOOLEAN DEFAULT true`

### New column
- `events.access_code` — `TEXT NULL` — 6-character alphanumeric code, set when `is_public = false`

### Publish flow fix
- `handlePublish()` in Step 4 currently hardcodes `is_public: false`. Must be changed to use the organizer's actual selection.

### Admin moderation fix
- `AdminDashboard.tsx` `handleModeration('approved')` unconditionally sets `is_public: true` on approval. This must be changed to **preserve the organizer's visibility choice**: only set `is_public = true` if the event was already `is_public = true` before moderation. For Private events, approval should set `is_approved = true` and `moderation_status = 'approved'` without touching `is_public`.
- The `fixPublicStatus()` utility must also be updated to only fix events where the organizer intended them to be public.

## Component Changes

### 1. Wizard Step 1 — `src/components/wizard/EventDetailsForm.tsx`

**Add after the Event Format section:**

- **Visibility selector**: Two buttons — "Public" (default) / "Private", styled like the existing event format selector
- **Access code field** (shown only when Private is selected):
  - Auto-generated 6-char alphanumeric code pre-filled
  - Editable text input for customization
  - Copy-to-clipboard button
- Regenerate button (generates a new random code)
- **Validation**: Access code must be non-empty, 4–10 alphanumeric characters when Private is selected
- **State**: `isPublic: boolean`, `accessCode: string`
- **Persistence**: Saved to localStorage via `saveEventBasicDetails()` and to Supabase via `saveDraft()`

### 2. Event Storage — `src/utils/eventStorage.ts`

**Add to `EventBasicDetails` interface:**
- `isPublic: boolean` (default: `true`)
- `accessCode?: string`

**Update `saveEventBasicDetails()` and `loadEventBasicDetails()`** to include these fields.

### 3. Event Wizard Hook — `src/hooks/useEventWizard.ts`

**Add to `EventDraft` interface:**
- `access_code?: string` (`is_public` already exists)

**Update `saveDraft()`** to include `is_public` and `access_code` in the Supabase upsert payload.

**Update `loadDraft()`** to read `is_public` and `access_code` from the fetched event.

### 4. Wizard Step 4 Privacy Section — `src/components/wizard/PrivacySection.tsx`

**Current state:** Local-only state, never saved. Must be fixed.

**Changes:**
- Accept `isPublic` and `accessCode` as props (read from event draft state)
- Display the current visibility choice and access code
- Allow toggling and editing (syncs back to parent state)
- Remove the isolated local `useState` for `publicEvent`
- **Note:** The other three toggles (`requireRegistration`, `showAttendeeList`, `allowSocialSharing`) remain as local-only UI placeholders — wiring them to the DB is out of scope for this feature

### 5. Wizard Step 4 Launch — `src/pages/06_Wizard_Step4_Launch.tsx`

**Fix `handlePublish()`:**
- Read `is_public` from the event draft state instead of hardcoding `false`
- Include `access_code` in the publish payload
- If `is_public = true`, set `access_code = null`

### 6. Browse Events — `src/components/discovery/BrowseEventsDiscovery.tsx`

**Query change:**
- Add `is_public` to the select columns

**EventCard interface:**
- Add `isPublic: boolean`

**Card rendering:**
- When `isPublic === false`, show a badge: lock icon + "Private" text
- Badge styled with a muted/dark background (e.g., `bg-gray-700/80 text-gray-300`), positioned similarly to existing badges

### 7. Event Landing Page — `src/components/events/DesignStudioLanding.tsx`

**Fetch change:**
- Already fetches `select('*')`, so `is_public` and `access_code` are available

**Display changes:**
- If `is_public === false`, show a "Private Event" badge near the event title
- All event content (details, speakers, agenda, etc.) remains fully visible

**Registration gate:**
- If `is_public === false` and user clicks Register/Get Tickets:
  - Show an access code modal/dialog before proceeding
  - Input field for the access code
  - "Submit" button validates against `event.access_code` (**case-insensitive** — input normalized to uppercase)
  - Input field uses `text-transform: uppercase` for visual consistency
  - Correct code → proceed to normal ticket selection/registration
  - Wrong code → inline error message "Invalid access code"
- If `is_public === true`: normal registration flow, no change

### 8. Registration Flow Page — `src/pages/32_Event_Registration_Flow.tsx`

**Guard against direct URL access:**
- On page load, fetch `is_public` and `access_code` for the event
- If `is_public === false` and no valid access code has been provided (via session/state), redirect to the landing page or show the access code modal inline
- This prevents bypassing the access code gate by navigating directly to `/event/{id}/register`

### 9. Admin Dashboard — `src/pages/admin/AdminDashboard.tsx`

**Fix moderation approval:**
- `handleModeration('approved')` must NOT unconditionally set `is_public = true`
- Only set `is_approved = true` and `moderation_status = 'approved'`
- Preserve the organizer's original `is_public` value
- Update `fixPublicStatus()` to only fix events where `is_public` was intended to be `true`

### 10. Event Duplication — `src/components/dashboard/EventsGrid.tsx`

**Duplicated events behavior:**
- Duplicated events reset to `is_public = true` (Public, draft state)
- `access_code` is set to `null` on duplication
- Organizer can set it to Private and generate a new code in the wizard

### 11. Access Code Generation Utility — `src/utils/codeGenerator.ts`

**Shared utility** (also used by the existing `generateConfirmationCode` in the registration flow):
```typescript
const UNAMBIGUOUS_CHARS = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'; // no 0/O, 1/I/L

export function generateAccessCode(length = 6): string {
  let code = '';
  for (let i = 0; i < length; i++) {
    code += UNAMBIGUOUS_CHARS[Math.floor(Math.random() * UNAMBIGUOUS_CHARS.length)];
  }
  return code;
}
```
- Extract the character set to a shared module
- The existing `generateConfirmationCode()` in `32_Event_Registration_Flow.tsx` should import from here

## Out of Scope

- Row-level security (RLS) policies in Supabase for access_code (access_code is validated client-side for simplicity; server-side validation can be added later)
- Invite-only events (email whitelist) — different feature
- Unlisted events (hidden from browse) — different feature
- Access code expiration or usage limits
- Wiring the other 3 PrivacySection toggles (requireRegistration, showAttendeeList, allowSocialSharing) to the database — they remain UI placeholders
- `07_Browse_Events_Public.tsx` (legacy browse page) — already filters `is_public = true`, so private events are excluded there by default. No changes needed.
- Organizer dashboard access code display post-publish (can be added as a follow-up in EventOverviewTab)

## Security Note

The `access_code` is stored in the events table and fetched with `select('*')`. For the MVP, client-side validation is acceptable since the event content is publicly visible anyway — only registration is gated. A future improvement could add a Supabase Edge Function to validate the code server-side without exposing it to the client.
